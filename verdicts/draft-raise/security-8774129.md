## Findings
- [medium] cli/wuwei/guards.py:149 blocks: yes. Failure: the ready door checks a different PR from the one gh changes. `_repo_number` takes the first bare number anywhere in argv and never reads `--repo=x/y` or `-Rx/y`. So `gh pr edit -t 5 7 --add-reviewer bob`, `gh pr edit --add-reviewer 5 7` and `gh pr edit --milestone 5 7 --add-reviewer bob` reach ready_door for PR 5, and `gh pr ready --repo=x/y 7` and `gh pr ready -Rx/y 7` reach it for origin's PR 7. When that PR is not a draft (or does not exist in origin but does in x/y), the call passes. Real gh 2.89.0 against a logging server sent `PullRequestByNumber {pr_number: 7}` followed by `requestReviewsByLogin {userLogins: [bob]}` and `title: "5"` for the first command, and `{owner: x, repo: y, pr_number: 7}` for both `--repo=` spellings. The guard probe with ready PR 5 and draft PR 7 (no gates) passed all five, so draft 7 gets a reviewer or leaves draft before its gates. The fix is to read the PR argument the way pflag does: the first positional word that is not a flag's value, plus `--repo=`/`-R<value>`. The merge door shares the same helper, so main also passes `gh pr merge --repo=x/y 5`.
- [medium] cli/wuwei/guards.py:185 blocks: yes. Failure: whether a REST create is a draft is decided from the `--input` file as it exists in the hook's cwd when the hook runs. gh reads the file in its own cwd when the command runs. `cd sub && gh api -X POST repos/o/r/pulls --input d.json` and `cp f.json d.json && gh api -X POST repos/o/r/pulls --input d.json` both pass the head guard because the hook-cwd d.json says `"draft": true`. Against the logging server gh sent `{"head":"b","base":"main","draft":false}` for both, which opens a non-draft PR before its gates. On main both reached the create door. A fix: count an `--input` draft only when the gh call is the command's only segment (no `cd`, writer or redirect before it), and otherwise treat it as not a draft.
- [medium] cli/wuwei/guards.py:188 blocks: yes. Failure: the endpoint is not normalised before the route table is matched. A doubled slash or a percent-encoded character misses the new ready routes: `gh api -X POST repos/o/r/pulls/7//requested_reviewers -f reviewers[]=bob`, `repos/o//r/pulls/7/requested_reviewers` and `repos/o/r/pulls/7/requested%5Freviewers` all pass on a draft with no gates. gh sends each path exactly as typed (logging server). github.com routes these paths: read-only GETs on taoq-ai/wuwei#1097 through gh returned `{"users":[],"teams":[]}` for the `//`, `o//r` and `%5F` spellings, the same answer as the plain path. POST routing is inferred from that and not measured. Collapsing `/+` and percent-decoding before the match closes it, and also closes the same gap on `pulls/5//merge`, which passes on main too.
- [medium] cli/wuwei/guards.py:160 blocks: yes. Failure: no test covers a short cluster that holds a reviewer. With `or m[3] and value is None` removed (mutant draft-cluster), tests/test_guards.py and tests/test_hook.py still pass, and `gh pr create -drbob` would read as a draft and pass. gh unpacks the cluster as `-d -r bob` (real gh: `gh pr create -dr` gives "flag needs an argument: 'r' in -r"), so the PR would open as a draft with reviewer bob requested before its gates. The code is right today. Add `gh pr create -drbob` (and `-fd`) to the held cases.
