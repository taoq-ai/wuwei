    Evidence¶

    A pull request is done when its safety evidence is complete. wuwei evidence owner/repo#n lists one PR's safety gaps; wuwei status lists every open item's. Each gap is actionable (the team can close it now), waiting (CI running, CI not started at a code head with no checks yet, the code host unreadable, an andon) or yours (an owner review).

    WUWEI never asks how the work was done. A test is in the diff or it is not; a reviewer passed this head or did not.

    Review statuses¶

    Some repositories publish their approval rule as a commit status, from a workflow that runs on pull_request_review (ai-stacks' Review Gate). WUWEI follows the status's target_url to its workflow run and compares the run's workflow with the workflows the repository has run on pull_request_review (its last 100 such runs, read once a day, and only when a head has an unsettled status). A match is review evidence, not CI:

    Status Gap
    pending waiting on review: <context>
    failure change request outstanding: <context>

    Both are actionable safety gaps: someone has to ask for a review or answer the change request, and the merge stays refused until then, with or without auto-merge. When the Actions host cannot be read, the status stays CI (CI running or CI failing), never a pass.

    Why: a review gate read as CI tells the team to wait for a build that already finished, or to fix a build that is not red.

    The spec engine¶

    When a repository uses a spec engine, its steps are part of the evidence at standard and full. WUWEI does not watch the steps run; it reads their artifacts at the PR head, in every feature directory the diff touches, so a later commit that only updates tasks.md still counts.

    Engine standard full adds
    spec-kit (.specify/, features in specs/<feature>/) spec.md, plan.md, tasks.md with every task checked (implement done) a ## Clarifications section in spec.md (clarify ran), analysis.md with no open CRITICAL or HIGH row (analyze ran clean), every item in checklists/ checked
    OpenSpec (openspec/, changes in openspec/changes/<change>/) proposal.md, at least one capability spec under specs/, tasks.md with every task checked

    Why: a spec nobody finished is worse than no spec, because it looks like agreement. Checking the artifacts, not the commands, keeps the rule true whichever way the steps were run.

    At standard the steps are process fit: a misfit is recorded, never blocking. At full they are safety gaps and hold the merge, because full is the tier for work where building the wrong thing is expensive.

    Breaking changes¶

    A change that breaks an outward contract (CLI commands and output, API endpoints and fields, config keys, events, schemas, formats other systems read) is close to a one-way door: the clients it breaks cannot be un-broken. WUWEI finds it three ways: the PR declares it (a ! in the title, a BREAKING CHANGE: line), the architecture gate states it (every arch verdict carries Breaking: no or Breaking: yes: <what breaks for which clients>), and a change to a contract file (OpenAPI, protobuf, GraphQL, JSON schema) takes the arch gate at any tier so it looks.

    Before such a change merges it needs evidence, in order:

    1. An Announcement: <link> line: the client communication, release note, migration guide or press release.
    2. Your confirmation, asked once the announcement exists: breaking: owner/repo#n at <sha7>: <what breaks>. Announced at <link>. Proceed?. It binds to that head; a change after it asks again.

    Why: a break nobody announced is an outage for someone else. The team does the work of finding and announcing it; you decide whether it ships.

    Gates before the PR, chosen by the diff¶

    The gates run before review: the PR opens as a draft so CI runs, and gh pr ready and reviewer requests are refused until the gates pass at its head, so reviewers and the merge only ever see gated code.

    The tier is a ceiling and the diff decides what runs under it:

    The diff Gates
    docs or specs only none
    code quality
    risky paths (auth, sessions, tokens, secrets, crypto, SQL, migrations, policies, infrastructure, CI, dependency manifests) or owner_paths, at standard + security
    a contract file (any tier), or more than 200 changed lines or 10 code files (standard) + arch
    full tier all four

    A one-line config flag costs one gate. After a fix round only the gate that found the problem re-reads. After review comments, a delta of docs, or of at most 20 lines off risky paths, carries the earlier passes; a larger one is re-read by the one gate it needs (security for risky paths, arch for a contract, quality otherwise). When the error budget is overrun, or a light item touches a trust path (auth, sessions, tokens, secrets, permissions, grants, policies) outside docs, the raised tier takes its full gate set.

    Why: gates that run after the PR opens race the merge, and four gates on a one-line change cost more than they find. Review cost follows risk.

    Attested verdicts¶

    A verdict counts only when WUWEI attested it. When a sentinel stops, the SubagentStop hook reads the file it names (Verdict file: <path>), checks its shape, and records its hash, gate, item, head, confidence and the agent that wrote it. A malformed verdict goes back to the reviewer once with the format. A file edited after attestation no longer counts, except that a finding (FIX or ESCALATE) still holds as recorded: replacing it cannot turn it into a pass. At one head, a later pass does not outvote a finding; a new head does. A seat that writes over another seat's verdict is sent back to write its own file beside it. When the stop cannot read the seat's last message, the handback to the lead carries it, and the verdict is attested from there. A verdict file that does not count is never silent: the board names it and why (its shape, or that no sentinel attested it).

    Why: a review is evidence only if a reviewer wrote it and it has not changed since. The hook checks the file at stop, however it was written, so a shell edit cannot slip past the lint.

    Duties¶

    A duty is work the team owes that does not hold the merge but reaches the team until it is done: asking for review where the team asks (see review requests), and, when a check is red, re-requesting an approval given at an older commit (the approval is named with its commit, so nobody re-runs a review gate that wants an approval at the head). Duties show on the board and in the Stop reminder, like safety gaps.

    Safety and process¶

    Only safety gaps hold a merge and reach the team while it works: a test, the gates at the head, green CI, answered threads, owner review, a breaking change's announcement and confirmation, the spec engine's steps at full, and evidence that can be read. Everything else is process fit: the plan link, the PR template, small batches, the Rollback: line, the spec engine's steps below full, a requested reviewer, staleness. Process fit never blocks and is never shown on the board or asked about; the merge records it, the report lists it, and the steward turns a rule that keeps misfiring, or keeps being skipped, into a fix.

    Why: continuous flow. Neither you nor the model should be distracted by a rule that does not fit this change. The audit still sees every misfit, and the process learns from them.

    Exceptions¶

    For a safety gap only, you can accept one gap at one head as an exception (see decisions). The gap disappears from that head's evidence, the exception stays on the record, and a follow-up item in the plan closes it later.

    When evidence cannot be read¶

    An unreadable code host is a waiting gap, never a pass. A merge whose evidence cannot be read stays refused.
