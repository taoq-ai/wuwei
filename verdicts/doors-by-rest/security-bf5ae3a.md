## Findings
- [high] cli/wuwei/guards.py:163 blocks: yes. Failure: an empty attached value (`-X=`, `--method=`, `-t=`, `-q=`, `--jq=`) is treated as "value in the next argument" because `m[2] or m[4]` is falsy for '', so `_api` swallows the next token and takes the method word as the endpoint. Real gh 2.89.0 reads `-X=` as the value "=" and `--method=` as "" without consuming anything, so `gh api -X= -X PUT repos/o/r/pulls/5/merge`, `gh api --method= -X PUT ...`, `gh api -t= -X PUT ...` and `gh api --jq= -X PUT ...` all sent `PUT /repos/o/r/pulls/5/merge` with the token (logging server, probe.sh). Main sends these to the merge door; head lets them through (pass), which is a regression. The same spelling also gets past the new refusals: `gh api -X= -X DELETE repos/o/r`, `gh api -q= -X PATCH repos/o/r/git/refs/heads/main ...`, `gh api -q= repos/o/r/pulls -f head=.. -f base=..` (create door skipped) and `gh api -X= -X POST graphql -f query='mutation{mergePullRequest...}'` all pass. Fix: decide whether to consume the next argument from whether the token had an attached part (`m[2] is None` and `m[4] == ''` with no `=`, or compare against the bare flag), and add these spellings to the route corpus.
