# Feature Specification: The docs site uses the same MkDocs Material layout and design as ZIRAN

**Feature Branch**: `392-mkdocs-site`

**Created**: 2026-10-03

**Status**: Draft

**Input**: Issue #392, docs(site): the docs site uses the same MkDocs Material layout and
design as ZIRAN, with a nav, both palettes and gh-deploy. Owner request of 2026-10-03.
Builds after #366 (same pages). References: ZIRAN `mkdocs.yml`, `.github/workflows/docs.yml`
and `docs/index.md` (copy the shape, not the content); #245 (the release asset ships
`docs/site`).

## Current state (read on main at b4b3b28)

- The site is Jekyll. `.github/workflows/docs.yml:22-25` runs `actions/jekyll-build-pages`
  over `./docs/site` and deploys with `actions/deploy-pages` (Pages source: GitHub Actions).
  `docs/site/_config.yml` sets `theme: jekyll-theme-cayman`.
- Every page in `docs/site` starts with Jekyll front matter (`---`, `layout: default`,
  `---`, lines 1-3) and all but `index.md` carry a `[Home](index.html)` breadcrumb on line 7.
  The pages cross-link with relative `.html` targets (more than 100 links over 12 pages),
  for example `daily.html#6-close`.
- There is no navigation: the only way between pages is the link list in `index.md:11-21`.
- The hero lives outside the site: `docs/assets/hero-light.svg` and `hero-dark.svg`,
  generated by `scripts/build-hero.py:339` and shown only in `README.md:2-6` through a
  `<picture>` element keyed on `prefers-color-scheme`. The site index shows no hero. No
  page under `docs/site` has a diagram.
- The integrity page lives outside the site too: `docs/integrity.md`. `docs/site/security.md:81`
  links to it as a GitHub blob URL, `README.md:92` as `docs/integrity.md`,
  `scripts/headless_e2e.py:148` copies it into the scratch source tree so `build-release.py`
  finds a `docs` directory, and `tests/test_docs.py:243,642` read it.
- ZIRAN (`mkdocs.yml`, `.github/workflows/docs.yml`): MkDocs Material, palettes `slate`
  and `default` with primary `indigo` and accent `cyan` and a brightness toggle, the
  features and markdown extensions the issue lists, an explicit `nav`, and a workflow that
  runs `uvx --with mkdocs-material mkdocs gh-deploy --force` with `contents: write`.
  ZIRAN's `docs/index.md` shows no hero; only its README picks a variant, with the same
  `<picture>` and `prefers-color-scheme` form WUWEI's README uses.
- Reproduced (read-only, a scratch copy of `docs/site` outside the repository, MkDocs 1.6.1
  with mkdocs-material through uvx): after stripping the front matter and breadcrumbs,
  rewriting `X.html` links to `X.md`, moving the integrity page and the hero SVGs under
  `docs/site`, and adding the ZIRAN config with `docs_dir: docs/site` and the nav below,
  `mkdocs build --strict` exits 0 with no warnings. Every existing anchor resolves under
  the MkDocs `toc` slugs. With MkDocs defaults a page left out of `nav` and a link to a
  missing anchor are only INFO and pass `--strict`; with `validation` set to `warn` for
  omitted files, anchors and unrecognized links, a planted orphan page, a planted bad
  anchor and a planted `.html` link each fail the strict build (exit 1).

## User Scenarios & Testing

### User Story 1 - The docs site looks and navigates like ZIRAN's (Priority: P1)

A reader opens https://taoq-ai.github.io/wuwei/ and gets the same layout as ZIRAN's site:
the Material theme, tabs for Home, Getting started, Concepts, Reference and Operations,
search, a light and a dark palette behind one toggle, copy buttons on code blocks and
permalinks on headings.

**Why this priority**: it is the owner's request; everything else serves it.

**Independent Test**: build the site with `uvx --with mkdocs-material mkdocs build --strict`
from the repository root and open `site/index.html`.

**Acceptance Scenarios**:

1. **Given** the branch, **When** `uvx --with mkdocs-material mkdocs build --strict` runs
   from the repository root, **Then** it succeeds with no warnings, where a broken link, a
   missing anchor and a page left out of `nav` would each be a warning and fail it.
2. **Given** the built site, **When** the reader toggles the palette, **Then** the page
   switches between the `slate` and `default` schemes with primary indigo and accent cyan.
3. **Given** the built site, **When** the reader opens the index in either palette,
   **Then** the hero shows the variant for that palette: the light SVG in `default`, the
   dark SVG in `slate`.

### User Story 2 - Pages are plain Markdown that the tests keep honest (Priority: P1)

A contributor edits a page in `docs/site` as plain Markdown: no Jekyll front matter, no
breadcrumb, links to `.md` files. The docs tests fail if a page is missing from the nav,
a relative link ends in `.html` or points at a missing file, or a page carries front matter.

**Why this priority**: without it the next page edit can break the strict build unseen,
because the suite runs on every pull request and the site build runs only on deploy.

**Independent Test**: `python -m pytest -q tests/test_docs.py`.

**Acceptance Scenarios**:

1. **Given** the docs tests, **When** they run, **Then** every page under `docs/site` is
   in `nav` and every `nav` entry is a page under `docs/site`.
2. **Given** the docs tests, **When** they run, **Then** no relative link in a site page
   ends in `.html`, every relative link points at a file under `docs/site`, and no page
   starts with front matter or carries the `[Home](index...)` breadcrumb.
3. **Given** the docs tests, **When** they run, **Then** the coverage tests for commands,
   configuration sections, headings and anchors still pass unchanged in what they check.

### User Story 3 - The site deploys from main with gh-deploy (Priority: P2)

The owner merges a docs change to main. The `Docs` workflow builds the site strictly and
pushes it to the `gh-pages` branch, the way ZIRAN does. The owner flips the Pages source
once, from GitHub Actions to the `gh-pages` branch.

**Why this priority**: it is how the change reaches the public URL; it can only be
checked after merge.

**Independent Test**: read `.github/workflows/docs.yml`; after merge, the workflow run
pushes `gh-pages`.

**Acceptance Scenarios**:

1. **Given** the merged workflow and the Pages source set to `gh-pages`, **When** a push
   to main touches `docs/site/**` or `mkdocs.yml`, **Then** the workflow deploys and
   https://taoq-ai.github.io/wuwei/ renders with the Material theme in both palettes and
   the hero shows the right variant for each.
2. **Given** a docs change with a broken link merged to main, **When** the workflow runs,
   **Then** the deploy fails and the live site keeps its previous version.

### User Story 4 - The release asset still ships the docs (Priority: P1)

An owner installs the signed `wuwei.tar.gz`. It still contains `docs/site`, now with the
integrity page and the hero, and the integrity check of the staged release passes.

**Why this priority**: #245 guarantee; a broken manifest blocks every install.

**Independent Test**: `python -m pytest -q tests/test_docs.py -k release_asset tests/test_headless_e2e.py`.

**Acceptance Scenarios**:

1. **Given** the release build, **When** it stages and signs the plugin, **Then**
   `docs/site` with every page and both hero SVGs is in the manifest and the archive, every
   README link resolves to a shipped file, and `integrity.measure` on the stage returns 0.
2. **Given** the headless end-to-end scratch build, **When** it stages its source tree,
   **Then** it finds the integrity page at its new path and the build and integrity check
   still pass.

### Edge Cases

- A link inside a page to an anchor on the same page (`#doctor`) stays as is; it has no
  file part to check.
- Links to files outside `docs/site` (the design spec, `templates/workspace/config.toml`,
  `agents/README.md`) stay absolute GitHub URLs; MkDocs cannot serve them.
- `docs/headless-e2e.md` and `docs/specs/` stay outside the site; they are not in `nav`
  and the nav test only covers `docs/site`.
- Viewing `docs/site/index.md` on GitHub shows both hero images one after the other; the
  palette selection works on the published site, and the README keeps its `<picture>`.
- A local `mkdocs build` writes `site/` at the repository root; it is ignored so it never
  reaches a commit or a development checkout's integrity fingerprint. The pattern is
  anchored (`/site/`): an unanchored `site/` would also ignore `docs/site/` and hide every
  new page and asset from git (found while building).

## Requirements

### Functional Requirements

- **FR-001**: The repository root MUST hold `mkdocs.yml` with ZIRAN's theme, palettes,
  features and markdown extensions, `site_name: WUWEI`,
  `site_url: https://taoq-ai.github.io/wuwei/`, `repo_name` and `repo_url` for
  `taoq-ai/wuwei`, `docs_dir: docs/site`, and a `nav` grouping Home; Getting started
  (daily, agent); Concepts (concepts, security); Reference (reference, configuration,
  adapters, charter-overrides); Operations (recovery, remote, rehearsal, integrity).
- **FR-002**: `mkdocs.yml` MUST set `validation` so a page omitted from `nav`, a link to a
  missing anchor and an unrecognized relative link are warnings, which `--strict` turns
  into a failed build.
- **FR-003**: Every page in `docs/site` MUST drop the Jekyll front matter and the
  `[Home](index.html)` breadcrumb, and link other site pages as `.md` with the same
  anchors. Every heading and anchor the existing tests and README links pin MUST stay.
- **FR-004**: The integrity page MUST move from `docs/integrity.md` to
  `docs/site/integrity.md`, and every reference to it (security page, README, headless
  end-to-end staging, tests) MUST follow.
- **FR-005**: The hero SVGs MUST move from `docs/assets/` to `docs/site/assets/`; the
  generator writes there, the README `<picture>` points there, and the site index shows
  the light variant only in the light palette and the dark variant only in the dark one,
  with the README's alt text.
- **FR-006**: `.github/workflows/docs.yml` MUST take ZIRAN's shape: `contents: write`,
  checkout, `astral-sh/setup-uv`, `uv python install`, and
  `uvx --with mkdocs-material mkdocs gh-deploy --force --strict`, on pushes to main touching
  `docs/site/**`, `mkdocs.yml` or the workflow, plus manual dispatch.
- **FR-007**: `docs/site/_config.yml` MUST be removed.
- **FR-008**: `CONTRIBUTING.md` MUST give the local preview command
  `uvx --with mkdocs-material mkdocs serve` and the one-time Pages source setting.
- **FR-009**: `tests/test_docs.py` MUST assert nav coverage both ways, no relative `.html`
  links, every relative link resolving to a file under `docs/site`, no front matter and no
  breadcrumb, the hero variants on the index, the workflow shape and the absence of
  `_config.yml`; its existing link assertions switch from `.html` to `.md`.
- **FR-010**: The release asset MUST keep shipping all of `docs` (unchanged
  `scripts/build-release.py`), and its test MUST expect the pages and hero under
  `docs/site`.
- **FR-011**: MkDocs and mkdocs-material MUST stay build-time tools run by `uvx`; no
  runtime import, no new Python dependency in `pyproject.toml`, no change under `cli/` or
  `adapters/`.

## Success Criteria

- **SC-001**: The strict site build passes with zero warnings on the branch.
- **SC-002**: 13 of 13 pages under `docs/site` appear in the nav, and 0 relative links end
  in `.html`.
- **SC-003**: The full test suite passes with no assertion removed except the three that
  pinned Jekyll (front matter, `_config.yml`, `.html` links), each replaced by its MkDocs
  counterpart.
- **SC-004**: After merge and the one-time Pages setting, the public site renders in both
  palettes with the matching hero in each.

## Assumptions

- ZIRAN's site shows no hero, so "the way ZIRAN serves its hero" is read as the README's
  per-scheme choice carried onto the site with Material's native `#only-light` and
  `#only-dark` image suffixes, which follow the palette toggle. A `<picture>` keyed on
  `prefers-color-scheme` would follow the OS setting and ignore the toggle.
- "Diagrams" in the issue means the hero: no page under `docs/site` has another diagram.
- The `integrity` nav entry means `docs/integrity.md`, moved into `docs/site` so it can be
  a page; moving the file is cheaper and clearer than an external nav link and keeps one
  copy.
- The hero moves into `docs/site/assets/` because MkDocs serves only files under
  `docs_dir`; one copy, with the README pointing at the new path, beats a duplicate.
- The hero is placed after the index's first paragraph, as raw HTML `<img>` tags carrying
  the README alt text: the first paragraph after the title is pinned by
  `test_readme_lead_and_limits`, and the glossary first-use test blanks HTML tags but not
  Markdown image alt text.
- `validation` in `mkdocs.yml` and `--strict` on `gh-deploy` go beyond ZIRAN's file; both
  are needed for the issue's statement that broken links and pages missing from `nav` fail
  the strict build, since MkDocs 1.6 reports those as INFO by default.
- The workflow triggers on `docs/site/**` rather than ZIRAN's `docs/**`, plus the workflow
  file itself as today; `docs/specs` and `docs/headless-e2e.md` are not part of the site.
- `mkdocs-material` is not pinned, as in ZIRAN; mkdocs-material currently constrains MkDocs
  below 2.0. Pinning is a follow-up if an upstream release breaks the build.
- The Pages source switch (Settings, Pages, Build and deployment, Source: Deploy from a
  branch, `gh-pages`, `/ (root)`) is a one-time owner action. This pipeline runs no `gh`
  command, so the PR body states it, with the API form for an owner token, and
  CONTRIBUTING documents it.
- The design spec has no section on the docs site; this issue does not touch any runtime
  behaviour, guard or state.
- No clarifying questions were asked (AGENTS.md); these assumptions stand in for them.
